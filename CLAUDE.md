# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Big Data Bowl project that measures receiver **heliocentricity** (gravity): how much tighter the real defense plays a receiver than a "ghost" defense would. The ghost is a conditional-VAE transformer (`src/ghost/model.py`). It sees the whole play's offense and ball tracking, the play context, and the defense only at the snap. From those it samples where a typical defense would go. It never sees player identities.

Data is BDB 2023 (2021 season, weeks 1–8) in `data/raw/bdb2023/` and BDB 2025 (2022 season, weeks 1–9) in `data/raw/bdb2025/`. Every frame has all 22 players plus the ball, so entities are never padded; only time is. Preprocessing cuts every play from the snap to the throw (or sack), so the model covers route development, not ball-in-air coverage. `data/raw/bdb2026/` holds the BDB 2026 data, which is unused. The pre-rewrite code lives outside the repo in `../big_data_bowl_legacy/`.

## Commands

```bash
uv venv --python 3.12 .venv && uv pip install --python .venv/bin/python -e '.[dev]'   # local setup
.venv/bin/python -m pytest                               # all tests (~2 s, synthetic data only)
.venv/bin/python -m pytest tests/test_model.py::test_prior_never_sees_hidden_defense

# `ghost` is the console script installed into .venv (use .venv/bin/ghost if the venv isn't active)
ghost preprocess                       # data/raw/bdb2023 -> data/processed/bdb2023.npz (+ .json metadata)
ghost preprocess --raw data/raw/bdb2023 --raw data/raw/bdb2025 --out data/processed/combined.npz   # both seasons in one cache
# then point train at it: ghost train --data data/processed/combined.npz --fold 0
ghost train --fold 0                   # one cross-fitting fold -> runs/default/fold0/{model.pt,metrics.csv}
ghost train --fold all                 # train on everything (no held-out plays)
ghost score [--include-blockers]       # needs every fold -> runs/default/scores/*.csv; player_scores.csv counts route runners only unless the flag is given
ghost sample-size [--include-blockers] [--eps 0.05 --quantile 0.9 | --delta YARDS]   # how many ghost samples score needs -> runs/default/sample_size/ (Longleaf: scripts/sample_size.sbatch)
ghost animate [--play-id N --game-id G] [--actual-call]   # random play by default -> runs/default/animations/*.gif
```

Every `ModelConfig` and `TrainConfig` field is also a CLI flag (`--d-model`, `--obs-frames`, `--epochs`, ...), except `n_dyn`, `n_glob`, `n_coverage` and `max_frames`, which come from the cache (`ghost preprocess --max-frames`, default 70: the longest snap-to-throw window kept; plays that throw later are dropped, not truncated). Use `--runs runs/<name>` to keep experiments apart. There is no linter or formatter configured.

**Local memory limit:** the dev machine is a MacBook with 8 GB of RAM total. Never run anything locally that could use more than about 4 GB. That rules out training, benchmarking, or scoring on the real cache (`PlayData.load` alone puts about 260 MB on the device, and a default-size model at batch 16 already overwhelmed the OS). Run real-data training and scoring on Longleaf. Locally, stick to `pytest` (tiny synthetic tensors), `ghost preprocess`, and small read-only checks of the data.

**Longleaf:** `data/` is gitignored, so copy `data/raw/bdb2023/` (about 950 MB) and `data/raw/bdb2025/` (about 8 GB) over separately. Then create the env from `environment.yaml`, run `pip install -e .`, then `ghost preprocess`, then `scripts/submit.sh [extra train flags]`. That submits a 5-task fold array (`train_folds.sbatch`) and a scoring job that waits for it (`score.sbatch`). Set `RUNS=runs/<name>` to choose the output dir. Logs go to `logs/`. The sbatch scripts call `$HOME/.conda/envs/ghost/bin/python -m ghost.cli` (override with `PYTHON=`) on the `a100-gpu` partition with `module load cuda/12.9`. `ghost score` defaults to the cache path saved in the checkpoints, so if you copy a run dir back locally, the matching cache has to be at the same relative path.

## Architecture

- **`preprocess.py`**: one pipeline for both releases. A `Source` spec (`SOURCES`, picked by `detect_source` from the tracking file names) holds each release's file glob, column renames and drop flags; the readers (`load_plays`, `load_player_groups`, `read_tracking`) rename to canonical 2025 spellings (`club`, `dropbackType`, `position`), and everything after them is season-agnostic. Only dropback passes are kept: run plays, QB runs, sneaks, spikes, kneels, plays nullified by penalty and scrambles are dropped (scrambles because the defense is no longer in its called coverage; `dropbackType` is not a model input). `play_window` finds the snap and the end frame (first `END_EVENTS` event, falling back to plays.csv `timeToThrow`/`timeToSack`) and drops plays with a handoff/run before the end. A play is kept only if every frame from the snap to the end has exactly 11 offense, 11 defense and the ball. 2025's split coverage variants are folded back via `COVERAGE_ALIASES`. The cache also stores `season`. Entity slots are fixed: offense sorted by nflId in 0–10 (`OFF`), defense in 11–21 (`DEF`), ball in 22 (`BALL`). Code everywhere indexes by these slices. Left-moving plays are rotated 180°. Angles use the NGS convention (`vx = s·sin(dir)`, `vy = s·cos(dir)`, checked against frame-to-frame motion). x is measured from the ball's x at the snap, and y from the field center. Positions are mapped to coarse groups (`GROUP_VOCAB`); WR, TE and RB are the receivers that get scored.
- **`data.py`**: `PlayData` loads the whole cache onto the device and builds batches by indexing, with no DataLoader. Splits are always **by game**: `game_folds` assigns folds, and `split_indices` also holds out `val_frac` of the training games for checkpoint selection.
- **`model.py`**: tokens are (frame, entity) pairs. Each `FactorizedBlock` attends over time within an entity, then over entities within a frame. Defender tokens at frames `>= obs_frames` have their features zeroed and a learned "hidden" embedding added. The prior sees only that masked input. The posterior encoder (training only) also sees the true defense. The latent has two parts: the coverage call `c` (PFF `pff_passCoverage`, bucketed into `preprocess.COVERAGE_VOCAB`) and a continuous per-play `z`. The prior gives p(c | context) and p(z | context, c). p(c | context) comes from a separate encoder pass over only the first `obs_frames` frames, because later offense movement reacts to the coverage and would reveal the real call. In training the decoder is teacher-forced with the true `c`, and the posterior q(z | context, true defense, c) is used. `forward` takes an optional `generator` for its posterior z draw; `train.evaluate` passes one seeded with `cfg.seed` for both that draw and its ghost samples, so validation metrics are deterministic but still an unbiased ELBO estimate. At sampling time `c` is drawn from the prior unless `sample(..., coverage=...)` fixes it. The decoder outputs defender positions as offsets from the last observed frame. The loss is a proper negative ELBO: a fixed-σ Gaussian (σ = 1 yard) summed over predicted frames, plus β·KL, plus −log p(c | context), with β annealed in `train.py`. The optimizer is AdamW with a per-step learning-rate schedule (`train.lr_factor`): linear warmup over `--warmup-steps` (capped at half the run's steps; the effective value is printed at startup), then cosine decay to `--min-lr-frac` × `--lr` at the last step. The schedule spans `--epochs`, so runs of different lengths have different schedules; `--lr-schedule constant` restores a fixed rate. The current rate is logged as `lr` in `metrics.csv`. The coverage label is a target only; it is never in `glob`.
- **`score.py`**: each play is scored only by the fold model that held it out (cross-fitting). For each receiver, at every predicted frame, `H_t = E[nearest ghost defender distance] − nearest actual defender distance`, and H is the mean over frames. Positive H means the real defense played the receiver tighter than expected. `H` uses ghosts that draw their own call (total gravity). `H_within` uses ghosts given the actual call (gravity within the call), and `H_call = H − H_within` is the part that acts through the play call. `two_ghosts` draws both ghost sets with the same generator seed (common random numbers), so `H_call` isn't swamped by independent z noise; keep that pairing if you touch sampling. `--samples` (K) defaults to 16. Raw H carries the model's miscalibration (a calibrated ghost has mean H of 0 within any group defined by inputs, yet the group means are positive and the bias grows with frame offset, and each fold model has its own). So `score_fold` also keeps per-frame `H_t` (and the within-call analogue) as compact `[rows, T]` arrays, padded to the cache's `max_frames`, and `H_centered`, `H_within_centered` and `H_call_centered` subtract the mean `H_t` of each (fold, position group, alignment at the snap, frame offset) cell before averaging over the play's frames. Alignment (`snap_alignment`: backfield / tight / slot / wide, stored as `align`) is in the cells because the ghost is looser on slot receivers than on wide ones, and alignment alone carried all of nearest-distance H's player-level reliability. Cells are computed over every WR/TE/RB row, blockers included. Offsets from the first one with fewer than `MIN_CELL_ROWS` (200) scored rows onward share one pooled cell. Centered H is zero frame-weighted within each cell, not row-weighted, so cell means of the per-play values are only approximately 0 when play lengths vary. The raw `H*` columns keep their meaning. Outputs are `play_receiver_scores.csv` (every WR/TE/RB row, with `ran_route` and `route_source`) and `player_scores.csv` (with names from `players.csv`). `player_scores.csv` aggregates only `ran_route` plays (pass-blockers aren't receivers) unless `--include-blockers`, adds for each centered H a `_mean` and a game-clustered `_se` (sandwich for a mean, times sqrt(G/(G-1)); NaN for a player seen in one game), is sorted by the main metric `H_dens8_centered_mean` (`MAIN_SIGMA`; falls back to `H_centered_mean` when σ = 8 isn't scored), and leaves out players with fewer than `--min-plays` aggregated plays (default: the lower quartile of players by play count; the cutoff is printed). `H_dens1` and `H_dens8` are the defender-density version (from the own-call ghost only): each defender counts exp(−d²/2σ²) at σ = 1 and 8 yards by default (`DENSITY_SIGMAS`; `--density-sigmas 1 2 3 ...` scores any set from the same ghost samples, which is how the bandwidth is tuned), and H_dens = real density − mean ghost density, centered the same way (`H_dens{σ}_centered`, with clustered SEs in `player_scores.csv`). It's unitless, credits double coverage and (at σ = 8) help, and far defenders barely count. σ = 8 was chosen on a 1–10 yd grid: its reliability held after adjusting for alignment, route shape and team, and it barely grows with play length; σ = 1 is kept as a tight-coverage measure. There is no shrinkage: with ~0.03 yd of true spread between players, empirical Bayes mostly pulled everyone to the group mean, so the ranking is the cutoff plus the SEs.
- **`routes.py`**: decides `ran_route`. BDB 2025 plays use `wasRunningRoute` from `player_play.csv`, read at score time from the cache metadata's `sources` dirs (`load_cross_fit` attaches it as `PlayData.route_labels`; the cache is unchanged; relative `sources` are also tried against the repo root derived from the cache path). `load_cross_fit` raises if any cached play with season >= 2022 has no label, so a missing `data/raw/bdb2025` can't silently fall back to the rule. Plays without a label (BDB 2023) use a tracking rule on the cached arrays: ended the window >= 5 yards from the snap position, or at x >= -2 (within 2 yards of the line of scrimmage or beyond). Rule vs label on 2022 plays, for "ran a route": all acc 0.929 / precision 0.959 / recall 0.963; WR 0.986 / 0.996 / 0.990; RB 0.834 / 0.926 / 0.861; TE 0.884 / 0.895 / 0.978. The rule is weakest for checkdown RBs and in-line TEs. `sample-size` also restricts to route runners by default.
- **`sample_size.py`**: reuses `score`'s cross-fit loading and `two_ghosts`. It draws many samples per held-out play (default 128), estimates the per-(play, receiver) spread s of the ghost distance, and recommends K = ceil((quantile of s / δ)²). By default δ = sqrt(eps · V), where V is the across-receiver variance of H net of Monte Carlo noise. It also splits H's variance into within-call and between-call parts. `--current-k` should match `score --samples`.
- **`animate.py`**: draws one play with its ghost defense, using the same held-out fold model and `heliocentricity` function as `score`. It runs `score.check_checkpoints`, so every fold must be trained first. The `runs/<name>/all` model from `--fold all` is not used by `score` or `animate`.

## Cross-file couplings

- `model.FEATURE_SCALE` scales the dynamic features by position in the list, so it must stay in step with `preprocess.DYN_FEATURES`. If you add or reorder a feature, update both. The input sizes (`n_dyn`, `n_glob`) come from the cache, so any preprocessing change means re-running `ghost preprocess` and retraining.
- Checkpoints don't store their held-out play indices. `score.py` recomputes them from the cache's `game_id` order plus `fold`, `n_folds`, `seed` and `val_frac` saved in the checkpoint. Don't re-preprocess between training and scoring, or the split changes. `score` loads the cache path saved in the checkpoints, and it refuses to run if the folds disagree on `n_folds`, `seed`, `val_frac` or the cache, if any fold is missing or extra, or if the cache's play-order fingerprint has changed.
- One full Longleaf pipeline has run: `runs/longleaf_default/` (copied back locally) holds 5 folds, `scores/` and a few animations. It used the BDB 2023-only cache with `max_frames` 50 (before the default became 70) and default hyperparameters, so it can't be re-scored against today's caches. Defaults are still untuned beyond that one run. It used a constant learning rate and unseeded validation sampling, so its validation numbers are noisier than newer runs' but the same estimator. Its per-epoch `metrics.csv` columns (`val_recon`, `val_kl`, `val_coverage_nll`, `val_coverage_acc`, `val_ade*`) are the place to compare experiments.

## Invariants the tests guard

`tests/test_model.py` checks that ghost samples don't change when defender tracking after `obs_frames` changes, when time-padded frames change, or when `batch['coverage']` changes (default sampling must draw its own call). They also check that the call logits are exactly unchanged by the label or by any frame after `obs_frames`. Any model change must keep these passing. If you add an input pathway, make sure it can't carry hidden defense information.
